SLIDE 1

Opening

0:45 · clock 0:45
Say

Hi everyone — welcome to lunch & learn number three. Today's question is the one behind every AI headline right now: what is an AI agent?

You've heard the word everywhere. By the end of these fifteen minutes you'll know exactly what it means — and you'll watch a real one do a real job, live. Spoiler: it's not magic. It's one surprisingly simple loop, the one at the bottom of this slide: think, act, observe, repeat.

Why this opening works You're making two promises — a definition and a live demo — and both get paid off. Naming “think → act → observe” now plants the phrase; by slide 4 it feels familiar instead of new.
SLIDE 2

Recap + the puzzle

1:00 · clock 1:45
Say

Quick rewind. Session one: a language model does exactly one thing — it predicts the next word. Look at the screen: “Once upon a…” — (pause) everyone in this call just finished that sentence in their head. Time. That's the whole machine. (point at the bars) The model holds candidates — “time”, ninety-four percent — picks the likeliest word, writes it down, and does it again for the next word. Not a database, not rules — what you just did, over and over, at scale.

And then in session two we watched Claude Code edit files and run commands on a real computer.

(pause) Those two facts don't fit together. If Claude is just a text predictor… how can Claude Code actually do things? Hold that question — it's the whole talk, and by the end you'll have the exact answer.

Background for you

The percentages on the slide are illustrative, not real model output — if anyone asks, say so plainly; the mechanism (a probability over next words, pick and repeat) is exactly right.

The tension is real, not rhetorical: a model's output is always just text — nothing else ever leaves it. Everything “agentic” comes from what other software does with that text. You resolve this twice: mechanically on slide 4, and by name on the formula slide after the demo.

SLIDE 3

Chatbot vs agent

1:00 · clock 2:45
Say

There are two ways to use the exact same model.

A chatbot is a consultant you call. Follow the little arrows on the left card: you ask, the model answers — and the arrow comes straight back to you, holding the hammer. “Which train should Jonas take?” It tells you. You still open the booking site. You do the work.

An agent is an assistant you brief. Look where the arrows go on the right: you hand it a goal, and then it's the model and the tools, back and forth, around and around — you're not in the middle anymore. It comes back when the job is done. Same brain. Different job description.

One line to remember: a chatbot answers. An agent acts.

And that's not my definition. Anthropic — the people behind Claude — define it in basically one line: (read the quote) “agents are models using tools in a loop.” Tools. In a loop. That loop deserves its own slide — let me draw it for you.

Background for you The on-slide quote is a faithful condensation of Anthropic's definition in “Building Effective Agents”: agents are “LLMs using tools based on environmental feedback in a loop.” If someone pushes on the definition, that's the authoritative source. The quote is also your transition machine: its last three words (“in a loop”) hand you slide 4.
SLIDE 4

The loop

2:00 · clock 4:45
Do This slide steps: press → seven times, one line of script per press. Don't rush — the diagram lights up as you speak.
Say — one beat per arrow press

0 · empty diagram — Here's the answer to the puzzle. Everything an agent does — every agent, from Claude Code to the demo you're about to see — is this one shape.

1 · Goal — It starts with a goal in plain words. No script, no flowchart — a sentence, like you'd brief a colleague. (point at the grey line) Ours: Jonas needs a train from Berlin to our Hamburg-Altona construction site, there by nine on Thursday.

2 · Think — Think: the model reads everything so far and decides what should happen next. And look at the line underneath — before it can pick trains or a hotel, it wants the site's exact address. Nobody told it to start there. It decided.

3 · Act — Act: it writes a request to use a tool — there it is: get_site, “Hamburg-Altona”. And notice — that request is just text. Text is still the only thing a model can produce. It hasn't done anything yet. It has asked.

4 · Observe — Observe: our code — normal, boring code — runs that tool and pastes the result back into the conversation: a street address. Now the model knows something it didn't know ten seconds ago.

5 · around again — Goal not met yet? Around again — but smarter. Address done — now it can go find trains from Berlin that arrive before nine, and everything it observed rides along in its context.

6 · Done — Nothing left to do? It answers. (pause) That's the whole trick. A text predictor, run in a loop, with code that acts on its requests. Keep this exact example in mind — in three slides you'll watch it happen for real.

Background for you

This is standard function calling (also called tool calling), and every major provider — OpenAI, Anthropic, Google — works exactly this way: the model outputs a structured request like find_journeys({from: "Berlin", to: "Hamburg"}), your application executes the real function, and feeds the result back. The model itself never executes anything.

Each tool result is the agent's “ground truth” — the moment it stops guessing about the world and gets real data. That's why agents beat pure chat on multi-step jobs: they check reality between steps.

SLIDE 5

Tools

1:15 · clock 6:00
Do This slide steps like the loop slide: press → twice (what counts as a tool → the four demo tools). The middle visual swaps, the caption at the bottom changes with you. One beat per press.
Say — one beat per arrow press

0 · definition — That orange Act card was a request — a request to use a tool. Here's the definition, and it's the whole slide: a tool is a capability someone built — handed to the model described in plain words. The model never runs it; it asks, our code executes.

1 · what counts — So what can be a tool? Anything code can do. In the demo, get_site is twenty lines of our own code. But it could just as well be an external API — Deutsche Bahn's timetable, Google Maps. A database lookup — a project, a schedule, a customer. Or a real-world action — send an email, create a ticket, edit a file. If code can do it, an agent can be handed it.

2 · the four tools — And these are, word for word, the four descriptions the model reads in the demo. That's the complete interface — no code, just these sentences. Two things to notice. The wording: “returns all options — check prices yourself.” Our tools do no thinking; they fetch; all judgement stays with the model. And the green lines: in the demo each of these is a little function I wrote — in real life the same slot would be the Bahn timetable API, Booking.com, your project database. Swap the code behind a description, and the agent doesn't change.

transition — So the tools decide what it can do. One question left before the demo: of the things it can do, how much do we let it decide without us? Different products answer that differently — and you already use most of them. That's the ladder.

Background for you Writing these descriptions well is a real engineering discipline — vague or overlapping descriptions make agents pick the wrong tool. If a developer asks “where do the descriptions go?”: they're sent with every API call, as JSON schemas with a name, description, and typed parameters. The model chooses among them by reading them — exactly like a new colleague reading a manual.
SLIDE 6

The autonomy ladder

0:45 · clock 6:45
Do Steps: press → to light rungs 1–4, one line each.
Say — one beat per rung

1 — Here's that ladder — four rungs, and the badges on the right are things you already use. Bottom: autocomplete — your phone keyboard finishing a word. Zero autonomy.

2 — Chat — a plain question-and-answer bot. It answers when asked; between answers, you do everything. ChatGPT started here — these days it climbs higher on this ladder, which is exactly why the ladder matters.

3 — Fixed workflow — a Zapier automation. The same steps in the same order every time, a pipeline with a model inside. Powerful, predictable — but someone decided the steps in advance.

4 — Agent — Claude Code, and the demo we're about to run. Nobody scripted the steps. It picks its own next move, checks the result, picks again — until the goal is met. Let's watch one do it.

Background for you Rung 3 vs 4 is the distinction practitioners actually argue about, and the accepted line (again from Anthropic's “Building Effective Agents”) is: workflows orchestrate models through predefined code paths; agents dynamically direct their own process and tool use. Their advice, worth quoting in Q&A: use the simplest thing that works — a workflow when steps are known, an agent only when you can't predict the path.

Cycle 1 · get_site — say while revealing Think, Act, Observe

Think card — First card: the model's own reasoning, live. Read it — it wants the site's exact address before it looks at hotels. Nobody told it to start there. That was its call.

Act card — The orange card is the request — look how small it is: get_site, name: Hamburg-Altona. That's all a model can do. Ask.

Observe card — And the green card is our code answering: the address on Harkortstraße, and the site manager, Petra. That's now in the model's memory — knowledge it didn't have ten seconds ago.

Cycle 2 · find_journeys

Think — Around the loop again — and notice it used what it learned: it has the address, so now trains.

Act / Observe — It asks for Berlin-to-Hamburg trains… and gets back seven. Here's the important bit: my code did zero filtering. Every train is in that table — expensive ones, late ones, all of them. The tool fetches; it doesn't think.

Cycle 3 · the money moment — slow down here

Think — This card is the whole talk. Read it out loud, slowly: only ICE 1601 — 6:55 to 8:45, 69 euros — fits both limits. The cheap trains arrive after nine. The early-enough trains cost more than eighty. Seven options, six ruled out, in plain language you can audit. A text predictor just did constraint-checking — because the numbers were in its context.

Act / Observe — Then hotels near the address from step one — eight come back, again unfiltered. The closest one, 800 metres away? A hundred and thirty a night — over budget. Watch what it does with that.

Cycle 4 · send_itinerary + Done

Think — It picks Hotel Altona Park — 95 euros, 1.2 kilometres, both limits met — and rules out the closer one for the price. Then, last part of the goal: send it.

Act / Observe — It writes the full itinerary itself — train, times, address, Petra's name — and our code “sends” it. Green check: delivered.

Done card — And it stops. Goal met, nothing left to do — remember the top arrow on the loop diagram.

Count what just happened: four tool calls, six trains and seven hotels rejected, zero lines of decision-making code in my program. Every decision happened in a blue Think card, in words. My code fetched data and delivered a message. That's an agent.

The formula

0:45 · clock 11:45
Say

Back to the slides — let's name what you just watched.

(walk the top row) An LLM — a text predictor. Plus tools — the four capabilities we handed it. Plus context — its memory: every request and every result stayed in the conversation, which is why cycle three could compare all seven trains. Plus the loop — decide, act, check, repeat until done. Plus actions — our code actually executing things. Add those up, and you have an AI agent.

(bottom row) And this answers where we started. An LLM predicts words. Claude — or GPT — is an LLM trained into a helpful brain you can talk to. And Claude Code is Claude, plus tools, plus this exact loop, running on your computer. (pause, point at the last line) That is how a text predictor ends up doing things. Slide two's mystery: solved.

Background for you This slide is deliberately 100% recap — every word on it has already been seen once. That's what makes it land. If you're behind on time, read just the equation and the final line; it still works in fifteen seconds.
SLIDE 9

Where it goes wrong

1:15 · clock 13:00
Say

Before anyone gets too excited — I showed you the run that works. Let me be honest about how this fails, because it fails in three characteristic ways.

It can loop forever — keep trying, never finish. And every trip around the loop is a paid model call, so that's real money and real time.

It can pick the wrong tool, with wrong arguments — confidently. It won't look unsure. It never looks unsure.

And the sneakiest: a bad assumption. It fills a gap with a guess, the guess lands in its context, and every later step builds on it. In our first test run, the goal didn't say where Jonas was starting from — so a lesser run might just guess a city. We fixed the goal, not the model.

So real agents ship with guardrails: cap the loops — ours stops after ten, no matter what. Limit the tools — it can send an itinerary; it cannot spend money. And for anything hard to undo, a human approves first. When Claude Code asks “may I edit this file?” — that's not the AI being polite. That's the guardrail. That's a human in the loop.

Background for you All three failure modes and all three guardrails are the standard ones in production-agent literature: bounded execution (step caps, budgets, timeouts), a minimal tool set, and human-in-the-loop checkpoints for high-stakes actions. The Jonas story is true — in our first live test the model asked which city Jonas was departing from instead of guessing. Honest detail if it comes up: the better failure is asking, and that's what it did.
SLIDE 10

The questions now

1:00 · clock 14:00
Say

So here's what this changes. The question about AI used to be: what can the model say? Is it smart? Does it hallucinate?

With agents, the questions become engineering questions — four of them, and you've met every one today.

Tools — what do we hand it? Every tool is a permission. The demo ran on four small ones; imagine tools that speak our world — “look up a project's schedule”, “draft a delay notification”. That's a thought, not a roadmap — but that's where the conversation starts.

Autonomy — what may it do alone, and where must a human approve? That's the ladder, applied to every job we'd give one.

Failure — what happens when it fails? Because it will: cap the loops, plan the fallback, make actions undoable. That's the previous slide as a checklist.

Trust — how do we check its work? Remember the blue Think cards — readable on purpose. An agent whose reasoning you can read is an agent you can audit.

None of these are solved problems. That's the honest state of this technology — and it's why it's worth understanding now.

Careful here Keep the Koppla examples clearly hypothetical — “imagine”, “a thought, not a roadmap” — unless you actually want to start that product conversation in the room. The slide's question is the takeaway, not any feature.
SLIDE 11

Close + questions

1:00 · clock 15:00
Say

Three things to walk away with.

One — an agent is not a new kind of AI. It's a language model, plus tools, running in a loop: think, act, observe, repeat.

Two — the model only ever writes text. Every real action — every file edited, every message sent — is ordinary code, written by people, acting on the model's requests. The power and the responsibility live in the tools we hand it.

Three — autonomy is a dial, not a switch. The craft is choosing the rung — and putting a human in the loop everywhere a mistake would hurt.

The demo and the slides are in the repo if you want to poke at them. Questions?

Q&A prep — likely questions

have these loaded
“Is ChatGPT an agent?”
“Mostly rung two — chat. But when it browses the web or runs deep research for you, it's climbing to rung four for that task: same loop we just watched, different tools.”
“What model / software was that? Did you use a framework?”
“An OpenAI reasoning model, called directly over their API. The whole loop is about twenty-five lines of code I can show you — no framework, no library. That's the point: the mechanism is small.”
“Could it book the train for real?”
“Same mechanism exactly — you'd swap my fake train tool for a real booking API. And that's precisely the moment you add the guardrail from slide 9: a human approves before money moves.”
“How is this different from Zapier / our existing automations?”
“Those are rung three — someone decided the steps in advance, and they run the same way every time. Great when the path is known! The agent chose its own path. Rule of thumb from the people who build these: use the simplest rung that works; agents only when you can't script the steps.”
“What about hallucinations?”
“That's actually where agents help: every Observe step pastes real data into the conversation, so it reasons over facts our tools returned, not memories. It can still make bad judgement calls — which is why the Think cards being readable matters. You can audit every decision.”
“Isn't this expensive / slow?”
“Each trip around the loop is one model call — this run was five, a few cents. The failure that costs money is the infinite loop, which is why every serious agent has a hard cap. Ours stops at ten.”
“Can it use tools it wasn't given?”
“No — and that's a feature. The tool list is the permission list. It can only ask for what we described to it; our code only executes what's on the list.”
“How does the model actually know which tool to pick?”
“Two things. First, it reads the descriptions — they sit in its context on every call, which is why writing them in plain words matters so much. Second, it was trained for this: model makers fine-tune on millions of examples of picking tools and filling in arguments, so it's a learned skill, like everything else it does. And deep down it's still next-word prediction — the ‘next words’ just happen to be a tool call.”
“Are the blue Think cards really how it thinks?”
“Honest answer: not the whole picture. Reasoning models do a longer, hidden scratch-work pass we never see; the blue cards are what the model writes to explain itself — its own commentary, not a brain scan. Still genuinely useful: it's what the model committed to in writing, and that's what makes its decisions auditable.”
“What's a reasoning model vs a normal one?”
“A normal model starts answering immediately. A reasoning model is additionally trained to first ‘think’ for a while — hidden scratch work, sometimes thousands of words of it — before answering. That makes it better at multi-step planning with constraints, like our four-constraints trip, but slower and pricier per call. The demo uses a reasoning model on its lowest thinking setting. Rule of thumb: quick lookup or rewrite — normal model; plan under constraints — reasoning model.”
“When was all this invented? It feels sudden.”
“Faster than it feels, actually. The idea — let the model reason, then act with tools — comes from research in late 2022, a paper called ReAct. Early 2023, Toolformer showed models could learn tool use. June 2023, OpenAI made function calling an official API feature — that's the moment this became a product thing, not a paper. Late 2024 brought a shared standard for plugging tools in, and by now it's how every major AI product works. About three years, paper to everywhere.”
“Will it remember Jonas next time? Does it learn from this run?”
“No. Each run starts completely blank — its only memory is the context window we watched filling up, and that's gone when the run ends. Products that seem to remember you do it by saving notes and pasting them back into the context next time. Which is session one again: everything the model knows in the moment is in its context.”
“Would it do exactly the same thing if you ran it again?”
“Not word for word — it's probabilistic, so phrasing and sometimes the order of steps vary run to run. The constraints keep the outcome consistent: every good run ends with the same train and hotel, because only one combination fits. That variability is real, though — it's why serious teams test agents the way they test software.”
“What's MCP? I keep hearing that term.”
“A standard plug for tools — think USB for agents. Instead of every app describing tools its own way, MCP is one shared protocol a tool exposes once and any agent can use. It came out of Anthropic in late 2024 and got adopted across the industry. Same concept as our four descriptions — just standardized.”
